# mockservers

## What it is

`mockservers` is a single hosted service that serves configurable mock HTTP endpoints from
definitions kept as files in this repository. Each **project** (`mocks/<slug>/`) declares its
endpoints with match rules and/or an imported OpenAPI 3 spec; response selection is driven by
the request (method, path, headers, query, JSON body), so you can steer a real downstream
workflow through any branch by choosing input values. No database, no runtime persistence, no
arbitrary user JavaScript. Full design: [`docs/specs/2026-08-28-mockservers-design.md`](docs/specs/2026-08-28-mockservers-design.md).

## Add a mock

```bash
npm run new-project <slug>     # scaffolds mocks/<slug>/project.yaml + routes/main.yaml
# edit mocks/<slug>/ — see docs/mock-format.md
```

Then open a PR. On merge, Vercel redeploys (~40s) and the mock is live at
`https://mockservers.dailyuze.com/m/<slug>/<path>`. Each PR also gets a Vercel preview
deployment — test the mock live on the preview URL before merging.

Authoring reference: [`docs/mock-format.md`](docs/mock-format.md).

## Local dev

Requires Node ≥ 20 (`package.json` `engines`). The machine default may be older — use nvm:

```bash
nvm use 22
npm install
npm run dev        # compiles mocks/ then starts Next on :3000
```

Run the gate before every PR:

```bash
npm run check      # compile + tsc --noEmit + eslint + vitest, in sequence; non-zero on any failure
```

## How it works

`mocks/` → `npm run compile` → `mocks.generated.json` (git-ignored build artifact) →
`app/m/[...slug]/route.ts` loads that object once into module scope and every request is an
in-memory lookup + linear scan of one project's routes. No database, no runtime I/O. The
bundle is regenerated by `prebuild` on every deploy, so it can never drift from `mocks/`.

**Do not rename `app/%5F%5Fmock/`.** Next.js 15 treats any `_`-prefixed folder as a private,
non-routable folder, so `app/__mock/` would silently 404 with no build error. The
URL-encoded `%5F%5Fmock` name is Next's documented opt-out and is what keeps `/__mock/health`
and `/__mock/projects` reachable. For the same reason `/m/<slug>/__spec` is handled inside
`app/m/[...slug]/route.ts` rather than as its own folder.

## Deploy / DNS

- **Vercel Hobby**, project imported from `github.com/KolaparthiDeepak/mockservers` under the
  owner's personal GitHub. Production deploys on merge to `main`; previews per PR.
- **Domain:** add `mockservers.dailyuze.com` in Vercel → Settings → Domains. Then in GoDaddy
  DNS add a CNAME: `mockservers` → `cname.vercel-dns.com`. TLS is auto-issued. Owning
  `dailyuze.com` already confers every subdomain; only a *wildcard* would need Vercel Pro.

## Deferred

Each gets its own spec later (see design doc section 13):

1. **Agent harness** — `.claude/` hooks (block commit on `main`, block force-push, enforce
   personal identity, validate `mocks/**` on edit), `AGENTS.md`/`CLAUDE.md`, GitHub Actions
   CI, `main` branch protection.
2. **Sandboxed JS handlers** — `export default (req) => response` run in an isolated context
   (no `require`/network/fs, time-boxed), for logic too branchy for `match` rules.
3. **Browser editing** — a KV store (Upstash Redis) + authenticated write UI; mock config
   becomes a document per project instead of repo files.
4. **Stateful mocks** — sequential/weighted response variants, call-count conditions; needs a
   per-project counter store.
5. **Multi-tenant / hosted-for-others** — auth, workspace isolation, quotas, abuse controls.
6. **OpenAPI schema faking** — synthesize response bodies for operations lacking examples.
7. **Wildcard subdomains** — `<project>.mockservers.dailyuze.com` (Vercel Pro).
